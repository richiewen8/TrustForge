# Certificate issuance and deployment pipeline

This document defines the durable stage protocol used by the PostgreSQL Worker. A job state identifies the next unit to execute. The processor performs at most one state unit per claim, persists any recovery checkpoint with the live lease token, and then appends exactly one state transition. A reclaimed job resumes from its persisted state and checkpoint.

## Stage protocol

| Current state | Work performed | Durable result / next state |
| --- | --- | --- |
| `Queued` | Start the pipeline without external side effects. | `Connecting` |
| `Connecting` | SSH host-key pin validation and remote helper health/protocol check. | `GeneratingCsr` |
| `GeneratingCsr` | Generate the service private key on the Linux target and return only its CSR. | Save CSR PEM; `CreatingOrder` |
| `CreatingOrder` | Create or recover the ACME order using the stable job ID and saved order URL. | Save order URL; `AwaitingChallenge` |
| `AwaitingChallenge` | Obtain DNS-01 challenges, checkpoint them, add exact TXT values through Technitium, wait for DNS and ACME authorization, then remove each job-owned value even after a failure. | `Signing` |
| `Signing` | Finalize the order with the CSR, download the public certificate bundle, and validate it against the CA root and the service registration. | Save bundle in the persistent artifact volume, record its reference and fingerprint; `Staging` |
| `Staging` | Send public certificate material to the fixed remote helper. The target combines it with the private key it generated earlier. | Record the staged deployment version; save release ID; `Activating` |
| `Activating` | Ask the fixed remote helper to atomically switch the current symlink, run the allow-listed reload action, and return the previous release ID. | Mark the deployment version Active and supersede the service's previous Active version; save previous release ID; `Verifying` |
| `Verifying` | Check the active certificate fingerprint, file ownership/permissions, and run the registered health action (which probes the served certificate). | Mark the deployment version Healthy, prune old releases per retention policy; `Succeeded`, or perform rollback and end in `FailedRolledBack` / `RollbackFailed` |

The simulator walks this state graph without making network calls, creating files, issuing a certificate, or claiming deployment success. It ends in the distinct terminal `Simulated` state.

## Recovery and checkpoint rules

- Checkpoint JSON is versioned with the job row and may contain only non-secret workflow references: CSR PEM, ACME order URL, certificate artifact reference, and deployment release IDs.
- Never persist a private key, SSH credential, ACME account key, DNS bearer token, or raw issued bundle in the job checkpoint. The private key is generated and retained on the Linux target. Issued public certificate material is kept in the persistent `trustforge-certificate-artifacts` volume.
- Every external mutation uses `jobId` as its idempotency/correlation key. A resumed step first checks the target system for the already-created resource before creating another one. ACME does not provide generic request idempotency; its adapter must save the order URL immediately and reconcile the account's existing orders if the process dies between order creation and checkpoint persistence.
- DNS cleanup removes only the TXT record matching both the challenge owner name and value. Challenges are checkpointed before the first record is presented and cleared after successful cleanup, so failure and lease-expiry recovery always knows exactly which records to remove. A resumed challenge stage reuses the checkpointed challenges; when every ACME authorization is already valid the stage advances without new DNS work.
- SSH verifies the configured OpenSSH SHA-256 host-key fingerprint before any command or upload. Commands are fixed helper operations selected by registered IDs; no user-controlled shell fragments or paths are accepted.
- A lease token fences all state/checkpoint writes. It cannot make an external side effect exactly once; adapters must reconcile after crash, and must stop if the lease is lost.
- The remote helper persists the previous symlink target before activation; repeating activation for the same job preserves that target. Activation and health-check errors trigger rollback and end in `FailedRolledBack` or `RollbackFailed`.

## Job submission and transactional wake

The `certificate_jobs` row is the durable queue — an outbox equivalent. Submission and processing are at-least-once: a job is claimed with `FOR UPDATE SKIP LOCKED` and a renewable fencing-token lease, and an expired worker's claim is re-claimed from its persisted state. No separate outbox table or in-memory signal is required for correctness; the durable row is the single source of truth.

To remove polling latency, job creation issues a transactional wake signal. `PostgresCertificateJobStore.TryAddAsync` inserts the job and issues `NOTIFY trustforge_job_submitted` on the same connection and transaction, then commits. PostgreSQL delivers the notification only on commit, so submission and wake are atomic: a rolled-back insert (including the `ux_certificate_jobs_active_service` conflict path) never wakes a worker. This covers manual submission and scheduler-driven renewal alike, since both create jobs through the coordinator's `TryAddAsync`.

The worker holds a dedicated `LISTEN` connection (`PostgresJobSubmissionChannel`, exposed as `IJobSubmissionChannel`) outside the pool (`Pooling=false`, `KeepAlive=30`, `ApplicationName=trustforge-job-listener`). When the claim loop finds no work it waits on this connection for up to `CertificateJobs:Worker:PollInterval` instead of sleeping, so a notification wakes it immediately. `CertificateJobs:Worker:NotificationEnabled` (default `true`, Compose `TRUSTFORGE_WORKER_NOTIFICATION_ENABLED`) selects this path; when disabled the worker simply polls. The first loop iteration always claims before listening, covering the startup window before `LISTEN` is established.

The notification is a latency hint, never a correctness dependency. A missed wake — process restart, reconnect, the startup window, or a database outage — only delays processing until the next poll; the durable row is still claimed. After a connection error the channel reconnects lazily with a short cooldown so a database outage cannot spin the loop. Scheduled retries (`next_attempt_at`) are not notification-covered; polling picks them up when due.

With multiple instances, `NOTIFY` broadcasts to every listener, but `SKIP LOCKED` plus a fresh fencing token per claim still guarantees a job is processed by only one worker. Npgsql buffers notifications received while the worker is busy, so the next wait returns immediately and no wake is lost between claims.

## Deployment versions, alerts and retention

- Every deployment writes a `deployment_versions` row keyed uniquely by job ID: `Staged` when the helper accepts the release, `Active` with the previous release ID after the atomic switch (the service's earlier Active row becomes `Superseded`), `Healthy` with a verification timestamp after fingerprint/permission/health checks. A successful rollback marks the failed release `RolledBack` and restores the superseded row it replaced; a failed rollback marks it `RollbackFailed`/`Unhealthy`. All writes are lease-fenced and forward-only, so stage replays are idempotent and an expired worker cannot rewrite history.
- Terminal failure transitions (`Failed`, `FailedRolledBack`, `RollbackFailed`) insert a `certificate_alerts` row in the same database transaction as the transition, so an alert can never be lost while the failure is recorded. Alerts carry kind, severity (`RollbackFailed` is Critical), failure stage and summary. Failure alerts reference their job (`job_id`); the column is nullable so the same table also holds job-less expiry reminders.
- `ExpiryReminderWorker` scans every `CertificateJobs:Expiry:ScanInterval` (default 1 hour) for enabled services whose Active deployment certificate satisfies `certificate_not_after <= now + CertificateJobs:Expiry:ReminderWindow` (default 7 days), independent of the renewal policy. For each it inserts a `CertificateExpiring` (Warning) alert with `job_id = NULL` and `dedupe_key = expiring:{serviceId}:{fingerprint}`. A partial unique index on `dedupe_key` makes this once-per-certificate: repeated scans do not create duplicate reminders, and a renewed certificate (new fingerprint) gets its own reminder. The scheduler runs only when the real worker is enabled.
- A dedicated delivery worker claims due alerts with `FOR UPDATE SKIP LOCKED` and a visibility timeout, delivers them at least once to the configured webhook (`CertificateJobs:Alerts:WebhookUrl`), or logs them as structured events when no webhook is configured. Receivers must dedupe by alert ID. Failed deliveries retry with bounded exponential backoff up to `MaxAttempts`, then end in delivery state `Failed`; a lost worker's claims become due again after the visibility timeout.
- After a successful verification the pipeline asks the helper to `prune` old releases: the active release, the recorded rollback slot, and the newest `CertificateJobs:Deployment:RetainedReleases` releases (default 3) survive; older release directories and their job key directories are removed. Pruning is best-effort — a failure is logged and never rolls back a verified deployment.
- Query endpoints: `GET /api/v1/services/{id}/deployment-versions` and `GET /api/v1/certificate-alerts` (optional `serviceId`, `deliveryState`, `limit`), both readable by PlatformAdmin, CertificateOperator and Auditor. `GET /api/v1/audit/export` (same roles) returns a JSON bundle `{generatedAt, filters, jobs, deploymentVersions, alerts}` with string-serialized enums, filterable by `serviceId`, `from`, `to`, `limit`, for compliance exports and incident timelines.

## Automatic renewal and concurrency guard

- Each managed service carries `renewalEnabled` (default false) and `renewalLeadTime` (default 30 days, validated positive and ≤ 365 days). Each deployment version records the issued certificate's `certificateNotAfter` at staging time.
- `RenewalSchedulerWorker` scans every `CertificateJobs:Renewal:ScanInterval` (default 5 minutes) for enabled, renewal-enabled services whose Active deployment version satisfies `certificate_not_after <= now + renewal_lead_time`, excluding services that already have an active job and services that already have a `renewal-scheduler` job created within `CertificateJobs:Renewal:MinimumRenewalInterval` (default 1 hour). For each candidate it creates a job through the coordinator with `requestedBy=renewal-scheduler` and idempotency key `renewal-{fingerprint}`. The fingerprint key means the scheduler never renews one certificate twice, and the minimum interval bounds the rate. Neither stops renewal when the window condition stays true: because a renewal replaces the Active version with a certificate whose `certificate_not_after` is the next one the scheduler reads, a lead time ≥ certificate lifetime keeps the service permanently in-window and the scheduler renews forever, one job per `MinimumRenewalInterval`. Configure `renewalLeadTime` strictly below the issued certificate lifetime; an operator who sets a longer lead time gets a throttled renewal cascade, not an idle service. The lab exercises exactly that case (25h lead time on 24h certificates) so the rate bound, not the steady state, is what is asserted. The scheduler runs only when the real worker is enabled (not in simulation).
- A partial unique index `ux_certificate_jobs_active_service` on `certificate_jobs(service_id)` covering only the nine active states enforces at most one active job per service at the database level. `POST /api/v1/services/{id}/certificate-jobs` maps the resulting unique violation to HTTP 409 `service_job_active`; the scheduler treats the same conflict as a lost race and re-evaluates on the next scan. This prevents duplicate concurrent renewal/deployment for a service.

## Revocation and CRL distribution

- `POST /api/v1/services/{id}/revocations` (policy `CertificateRevoker`, i.e. `PlatformAdmin` only — narrower than the `CertificateOperator` policy that allows issuance, because revocation is irreversible for a certificate) requires an `Idempotency-Key` header and a `reason` of `Unspecified`, `KeyCompromise`, `CaCompromise`, `AffiliationChanged`, `Superseded` or `CessationOfOperation`. `GET /api/v1/services/{id}/revocations`, `GET /api/v1/certificate-revocations/{id}` and the audit export stay on `CertificateReader`.
- The request is bound to real material, not to caller input: the service's `Active` deployment version supplies the job, that job's stored artifact supplies the leaf PEM, and the artifact fingerprint must equal the deployment version fingerprint before anything is sent to the CA. Outcomes are `200 revoked`, `202 pending`, `200 replayed`, `409 service_job_active`, `409 no_active_certificate`, `404` unknown service.
- The recorded serial is the CA-side serial: .NET's `SerialNumber` keeps the DER INTEGER sign pad, so a leading `00` is stripped, which is what step-ca's CRL and `openssl x509 -serial` print.
- `ICertificateRevocationChannel` uses the ACME `revokeCert` endpoint advertised by the directory, signed with the same account key that issued the certificate (`SmallstepAcme:AccountKeySecretRef`). step-ca authorizes only the issuing account, so the target's private key is never needed and never leaves its host; an `alreadyRevoked` error is treated as success so replays converge. The `revokeCert` URL is read from the directory rather than derived from the configured path, and the payload (`resource`, base64url `certificate`, integer `reason`) is passed to Certes as an **object**: `AcmeContext.Sign` serializes and base64url-encodes the payload itself, so a pre-serialized JSON string is encoded twice and step-ca answers HTTP 500 (`cannot unmarshal string into Go value of type api.revokePayload`). step-ca also rejects `Content-Type` with a charset parameter, so the POST sends bare `application/jose+json`, and one `badNonce` retry is taken because nonces are single-use.
- Durability mirrors the alert outbox: the CA success and its `CertificateRevoked` audit alert are committed in one transaction, a failed attempt keeps the row `Pending` with exponential backoff, and `RevocationRetryWorker` claims due rows with `FOR UPDATE SKIP LOCKED`, a visibility timeout and an `attempt_count` optimistic-concurrency guard. After `CertificateJobs:Revocation:MaxAttempts` the row turns `Failed` and a critical `RevocationFailed` alert is raised. `ux_certificate_revocations_live_serial` (partial unique on `serial` where `state <> 'Failed'`) keeps at most one live row per certificate, and the idempotency key makes a retried request return the original record.
- The API attempts the CA inline, in the request. A freshly inserted `Pending` row carries `next_attempt_at = NULL`, which `ClaimDueAsync` treats as due, so `RevocationRetryWorker` can claim the same row while that inline attempt is still in flight — normally when the CA is slow or unreachable and the request is still waiting. This is expected and benign: both writers address one serial, the CA call is idempotent per serial (`alreadyRevoked` converges to success), and the `attempt_count` guard makes the writes forward-only, so exactly one of them records the outcome and the row can never regress or double-count. Consequently the `lastError`/`attemptCount` a client reads back right after a `202 pending` may have been written by the worker rather than by the request; which writer won is not a correctness property, that the row is `Pending` with a scheduled next attempt is.
- Alert severity encodes urgency: `KeyCompromise` and `CaCompromise` raise `Critical`, other reasons `Warning`, deduped by `revoked:{serial}`.
- Revocation does not touch the deployment: the version stays `Active` and the target keeps serving the revoked leaf until the next issuance replaces it. Issue a new certificate right after revoking one you intend to stop using.

CRL distribution is a CA-side setting that step-ca ships disabled: `ca.json` needs a `crl` block (`enabled`, `generateOnRevoke`, `renewPeriod`, `cacheDuration`, `idpURL`) and a restart, after which the list is served at `GET /1.0/crl` on the CA port and already-stored revocations appear in it. Two limits matter for operators: leaves are issued **without** a CRL Distribution Points extension even when `idpURL` is set (verified on v0.30.2), so relying parties must be pointed at the CRL URL out of band, and OSS step-ca has no OCSP responder. TrustForge's own deployment verification keeps `X509RevocationMode.NoCheck` — it proves the chain builds against the configured root and matches the deployed fingerprint, while revocation status is asserted against the CA's CRL by the revocation flow and its drill.

## Adapter contracts

`ICertificateIssuer` owns ACME order/authorization/finalization; `IDnsChallengeProvider` owns narrowly-scoped DNS-01 record create/propagation/cleanup; `ILinuxCertificateDeployer` owns pinned SSH, target-side CSR generation, staged deployment, activation, health/fingerprint verification, and rollback; `ICertificateRevocationChannel` owns the CA-side revocation of an issued leaf. These interfaces pass stable job IDs and persisted references so their implementations can be retried after a process restart.

The development simulation is opted in only when `ASPNETCORE_ENVIRONMENT=Development` and `CertificateJobs:Simulation:Enabled=true` (Compose: `TRUSTFORGE_SIMULATION_ENABLED=true`). It automatically enables the Worker and cannot be enabled in Production. Set `CertificateJobs:Worker:Enabled=true` for real execution; install the Linux helper and service/action registrations using [remote-helper/README.md](remote-helper/README.md), configure Smallstep ACME and Technitium DNS, and mount the artifact volume persistently.

The ACME order URL is checkpointed immediately after creation. When no order URL is checkpointed, the issuer reconciles the account's existing orders before creating a new one: it lists them with a signed POST-as-GET request (step-ca returns a bare JSON array; RFC 8555 servers wrap it in an `orders` property) and reuses the newest unexpired `pending`/`ready` order whose identifiers exactly match the approved service SANs. Orders already `processing` or `valid` are never reused because their certificate was finalized against a different CSR. Persisted and newly created orders pass the same exact-identifier check. A database-level partial unique index enforces at most one active job per service (see "Automatic renewal and concurrency guard"), so concurrent jobs for the same service are rejected at creation; the signing stage's CSR-to-certificate public-key check remains as defense in depth before anything is deployed.

Known CA defect: step-ca's nosql ACME backend (v0.30.2, still unfixed upstream at the time of writing) corrupts the account order index when orders are listed after every order of the account has completed — it stores empty bytes, and every later new-order/list for that account fails with HTTP 500 (`error unmarshaling orderIDs ... unexpected end of JSON input`, or `changed since last read` on the empty-index create path). Reconciliation triggers this on unpatched servers. The development lab builds step-ca with a two-line fix (`dev/acme-lab/step-ca/Dockerfile`); production step-ca deployments need the same patch or a fixed release.

Before an issued bundle is persisted or deployed, the signing stage validates it: the chain must build against the configured Smallstep root, the leaf fingerprint must match the signing result, the certificate public key must equal the target-generated CSR's public key, SANs must exactly equal the registered service SANs, EKU must permit server authentication, the key must be RSA ≥ 3072 or ECDSA nistP256/384/521, and the validity window must be current and within `SmallstepAcme:MaximumCertificateLifetime`. The CSR itself is validated for SANs and key strength when it is first collected.

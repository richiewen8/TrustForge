# TrustForge 0.1.0

First release that can be installed from GitHub Releases. TrustForge combines internal PKI and
certificate lifecycle management with the Technitium DNS Server engine in one Linux application; the
DNS engine runs inside the TrustForge process, PostgreSQL is its data service, and an external OIDC
provider supplies API identity.

What is new in this release is the delivery path: the CI workflow
([`.github/workflows/linux-release.yml`](https://github.com/richiewen8/TrustForge/blob/master/.github/workflows/linux-release.yml))
builds the application, packages it, validates the package, and publishes the assets here. Until now
`deploy/bare-metal/install.sh` could only build from a source checkout on the target; it can now
install from these assets with no compiler, no source tree and no sibling library checkout on the
host.

## Install from this release

```sh
sha256sum -c trustforge-0.1.0-linux.tar.gz.sha256
tar -xzf trustforge-0.1.0-linux.tar.gz
cd trustforge-0.1.0-linux
sudo bash deploy/bare-metal/install.sh --check-only      # read-only preflight
sudo bash deploy/bare-metal/install.sh --dry-run         # preflight, then print the plan
sudo bash deploy/bare-metal/install.sh \
    --oidc-authority https://id.internal/realms/trustforge \
    --oidc-audience trustforge-api
```

The host must be Ubuntu 24.04 on systemd, not a container, with ports 53/tcp+udp, 5380/tcp and
5000/tcp free, and outbound HTTPS to `dot.net` (the ASP.NET Core 10 shared runtime) and
`apt.postgresql.org` (PostgreSQL 17, unless `--skip-postgres`). The installer is `100755` in the
archive and refuses to run as a non-root user, on a non-systemd host, or inside a container.

Read [`BAREMETAL.md`](https://github.com/richiewen8/TrustForge/blob/master/BAREMETAL.md) before the
first run: secret paths (`/etc/trustforge/secrets`, `0750 root:trustforge`, read-only to the service)
and the DNS settings frozen at first boot are decisions that are expensive to undo.

## Assets

| Asset | What it is |
| --- | --- |
| `trustforge-0.1.0-linux.tar.gz` | `app/` (framework-dependent publish output), `deploy/bare-metal/`, `docs/`, `MANIFEST.json`, `SHA256SUMS` |

`-linux` rather than `-linux-x64`: the publish is RID-less, architecture-neutral IL.

## Provenance

`MANIFEST.json` records the TrustForge commit, the `TechnitiumLibrary` commit
(`4a5a530ac6c4114e72216e0b9c74208a7a5e3fa0`, tag `dns-server-v15.6.2`), the DNS engine version
(15.6.2), `publishMode: framework-dependent` and the required shared runtime
(`Microsoft.AspNetCore.App 10.0`). Those application bytes are `docker cp`'d out of the build stage of
the repository's own `Dockerfile`, so the package and the container image are the same build rather
than two builds that were compared afterwards.

## What CI proves, and what it does not

The workflow proves, on every tag: that the tag equals the `<Version>` declared by
`TrustForge.Api/TrustForge.Api.csproj`; that the library checkout is the pinned commit; that all five
assets exist, that both detached checksums verify, and that `SHA256SUMS` verifies inside the archive;
that `install.sh --validate-package` accepts these assets and rejects archives carrying a symlink
member, an absolute member name, a `*.env`/`*.key` file, a lost exec bit, or a byte that no longer
matches its recorded checksum; that `deploy/bare-metal/install.sh`, `deploy/release/make-package.sh`,
`deploy/bare-metal/build-and-verify-in-container.sh` and the packaged copy of the installer pass
`bash -n` and `shellcheck -S style`; that the packaged unit file parses under `systemd-analyze verify`;
that the downloaded assets round-trip from the published release.

It does **not** prove that TrustForge installed and ran on a machine. The runner is not physical
hardware and the installer refuses to run there by design, so no service was started, no migration
was applied, `CAP_NET_BIND_SERVICE` was never exercised on port 53, the loopback-only binds on 5000
and 5380 were never observed, and the PostgreSQL 17 provisioning path was never run.
[`BAREMETAL.md` — On-target checklist](https://github.com/richiewen8/TrustForge/blob/master/BAREMETAL.md)
is the only installation evidence for a release until someone completes it on a real host, and the
maintainer of this repository has not done that for 0.1.0.

## Capability status

Working: PostgreSQL persistence for managed Linux services, certificate jobs and job state history;
OIDC JWT authentication with role-based API authorization; service registration and certificate job
APIs; the embedded DNS service with its protocol ports and administration console; SSH host key
fingerprint based deployment records with external secret references. Certificate issuance, durable
worker execution, SSH certificate deployment, health checking, rollback and scheduled renewal remain
staged work — see `IMPLEMENTATION-PLAN.md`. The DNS web console still authenticates separately from
the TrustForge API.
